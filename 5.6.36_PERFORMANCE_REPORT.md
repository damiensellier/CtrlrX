# Large-panel load investigation — KronosKontrol / CtrlrX 5.6.36

**Context:** This report details the performance bottlenecks found when loading large panels (20–30 MB) in CtrlrX 5.6.36 (JUCE 6.0.8). The issues were originally discovered while developing the ~30 MB "Kronos Kontrol" panel, which caused the application to freeze for ~30 seconds, consume 741 MB of RAM, and take 4.5 seconds just to show the window.

## 1. The Result
By applying four targeted optimizations, we achieved the following on the 30 MB panel (895 modulators):
- **Window appearance:** 4.46 s → **0.68 s**
- **Panel load:** ~30 s → **1.87 s**
- **Peak RAM:** 741 MB → **156 MB**

## 2. The Bottlenecks & Fixes

### 2.1. The JUCE XML Parser O(n²) Bug
*The 30-second freeze.*
89% of the load time was spent inside `juce::XmlDocument::parse`. The panel stores 20 MB of base64 images and 6.6 MB of Lua code inside XML attributes. JUCE's `readQuotedString` appends these attributes character-by-character using `String::appendCharPointer`. Because `juce::String` allocates exact sizes and calls `strlen` on every append, parsing required copying over 130 GB of data.
*   **The Fix:** Rewrote `readQuotedString` to accumulate bytes in a `MemoryOutputStream` and convert to a `String` exactly once. 
*   **Result:** XML parsing dropped to **185 ms**. (Patch provided: `patches/juce6_xml_parser_perf.patch`)

### 2.2. The Eager Resource Importer
*The 3-second delay after XML.*
On every launch, `CtrlrPanelResourceManager::importResource` base64-decoded 20 MB of images and wrote 228 PNGs to disk, even if they already existed.
*   **The Fix:** Added an on-disk cache check *before* the in-memory registry check and *before* decoding. Added a source/destination guard to prevent truncation. 
*   **Result:** Resource registration is now **359 ms** (228 hits, 0 misses, 0 writes).

### 2.3. The Eager Image Decoding
*The RAM bloat.*
`guessType()` called `ImageCache::getFromFile()` to figure out what type of file it was looking at, forcing all 228 images to decode into RAM just to check their extension.
*   **The Fix:** Replaced with an 8-byte header magic check (PNG/JPEG/GIF/BMP) plus extension fallback. 

### 2.4. The Lazy Font Enumeration (The Startup Killer)
*The 4-second pre-window delay.*
Profiling revealed a massive delay in the `CtrlrManager` constructor. We initially suspected `Font::findAllTypefaceNames()`, but measurement showed that only took 26 ms. The true culprit was the very next line: `Font::findFonts(osFonts)`. In JUCE 6 on Windows, this uses GDI to instantiate a full `Font` object for every face on the system, costing **3,921 ms**.
*   **The Fix:** Deferred `findFonts()` via `ensureOSFontArray()`. `getFontSetEnum()` now classifies from the always-loaded names array, preserving font-set semantics. The heavy Font array is only instantiated the first time the font picker UI is opened.
*   **Result:** Font constructor dropped from **3,967 ms to 113 ms**.

## 3. Phase Breakdown (Final)
- **Startup / Font init:** 113 ms
- **XML Parse:** 185 ms
- **Lua Restore (41 methods):** 97 ms
- **Resource Import (228):** 359 ms
- **Widget Construction:** 349 ms
- **Total:** 1.87 seconds

## 4. PR #337 (Panel Probe) & JUCE 8 Context
The engine load is now fast enough that headless testing is practical. We successfully integrated PR #337 into the 8.x branch (JUCE 8.0.12). It runs a full suite of 34 scenarios against this 30 MB panel in **2.9 seconds**. 

**⚠️ Note for JUCE 8:** When porting PR #337 to 8.x, we found that JUCE 8 uses native asynchronous dialogs (`AW::`), meaning the probe can no longer auto-dismiss `AlertWindow` calls. We marked this scenario as `SKIP`. If the probe is to be fully robust in the 8.x era, the engine may need a headless dialog policy.
